## 선수 수정 실검증

기존 선수의 체중 값을 사용해 되돌릴 수 있는 쓰기 검증을 수행했다.

1. 기존 값 `90kg`을 확인했다.
2. 검증 사유와 함께 `91kg`으로 저장했다.
3. 상세 화면에 `91kg`과 변경된 업데이트 시각이 표시되는지 확인했다.
4. 원복 사유와 함께 `90kg`으로 다시 저장했다.
5. 상세 화면이 `90kg`으로 복구됐는지 확인했다.
6. 데이터 관리의 관리자 로그에서 변경과 원복 사유, 작업자 기록을 확인했다.

개발과 운영 모두 최종 데이터는 원래 값인 `90kg`이다. `manual_overrides`에는 현재 원복 값이 활성 보호값으로 남아 이후 SportsMonks 동기화가 이 값을 덮어쓰지 않는다.

## 발견한 오류와 조치

### CloudFront Function 실행 오류

- 증상: 모든 운영 경로가 HTTP 503과 `FunctionExecutionError`를 반환했다.
- 원인: CloudFront Functions 런타임 지원 범위를 벗어난 optional catch binding(`catch {}`)을 사용했다.
- 조치: `catch (error)` 형태로 변경하고 운영 Function을 다시 publish했다.
- 결과: `/login/` HTTP 200, 배포 스모크 테스트 통과.

### Next.js 정적 데이터 요청 오인

- 증상: 선수/사용자 상세에서 메뉴를 누르면 `...?userId=index.txt` 같은 잘못된 상세 주소로 이동했다.
- 원인: viewer-request Function이 Next.js 정적 탐색 파일 `/users/index.txt`를 기존 동적 상세 ID로 해석했다.
- 조치: 상세 ID 리디렉션에서 점이 포함된 파일명을 제외하고 회귀 테스트를 추가했다.
- 결과: 상세 → 목록 이동 시 `/users/`가 유지되고 데이터가 정상 표시됐다.

### 개발 선수 수정 RPC 누락

- 증상: 개발에서 선수 저장 시 “선수 상세 수정 SQL을 먼저 적용해 주세요”가 표시됐다.
- 원인: 개발 DB에 `manual_overrides`와 일정 RPC는 있었지만 `admin_update_player_details(...)` 확장 RPC가 없었다.
- 조치: `supabase/manual/player_detail_editing.sql`을 정식 migration `202609070005_player_detail_editing.sql`로 추가하고 개발 프로젝트에 적용했다. 원격 migration 이력도 적용 상태로 기록했다.
- 결과: 개발 선수 수정·원복과 감사 로그 기록 통과.
